# The PostgreSQL dialect tree

The same schema as `pipeline/migrations/`, in PostgreSQL's dialect. **Same
filenames, same order, same `schema_migrations` ledger.** A file here is the
port of the file one directory up with the identical name, and it must
produce the same objects, columns, constraints and semantics.

Identical filenames are the point. They make the two trees diffable by a
person and by `tests/test_migration_equivalence.py`, which compares the object
inventories the two produce. A file added to one tree and not the other fails
that test rather than being discovered a month later by a query that returns
nothing.

## When you add a migration

Write both. `0034_thing.sql` in both directories, in the same commit. The
equivalence test will tell you if you forgot, but the reason to do it in one
commit is that the two files are one decision.

## The conversions, and why each one is what it is

| SQLite | PostgreSQL | Note |
|---|---|---|
| `TEXT` | `text` | |
| `INTEGER` | `bigint` | SQLite's `INTEGER` is already 64-bit. `integer` would narrow it. |
| `REAL` | `double precision` | Bit-identical. Not `numeric` — `SUM` semantics differ, and every figure in this warehouse came out of a `REAL`. |
| `INTEGER PRIMARY KEY AUTOINCREMENT` | `bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | See below. |
| `CREATE TRIGGER IF NOT EXISTS` | `CREATE OR REPLACE TRIGGER` | PostgreSQL has no `IF NOT EXISTS` for triggers. `OR REPLACE` needs 14+. |
| `SELECT RAISE(ABORT, '…')` | a `plpgsql` function raising with `ERRCODE` | See below. |
| `GROUP_CONCAT(x, ', ')` | `string_agg(x, ', ')` | Order is unspecified in both. |
| `GROUP_CONCAT(DISTINCT x)` | `string_agg(DISTINCT x, ',')` | SQLite's one-argument form uses `,`. |
| bare column in `GROUP BY` | an aggregated subquery, joined | PostgreSQL rejects it; see `0025`. |
| `CREATE VIEW IF NOT EXISTS` | `CREATE OR REPLACE VIEW` | Replacing requires the same column names and types, which is what we want to be true anyway. |

### Identity columns are `BY DEFAULT`, not `ALWAYS`

`GENERATED ALWAYS` is the stricter and normally the better choice: it refuses
an insert that supplies its own id. Two things here argue against it.

`job_runs.id` is allocated by the application — the job registry continues
from `max(id)` and has to be able to say which id it chose — so that one has
to be `BY DEFAULT` whatever the others are.

And the Phase 2 data migration copies ids verbatim from the SQLite warehouse
so that every foreign key and every recorded `evidence_promotions.id` still
points where it did. Under `GENERATED ALWAYS` each of those inserts needs
`OVERRIDING SYSTEM VALUE`, which is a modifier the loader would have to add
per table and could silently omit on one of them.

One rule for all seven columns is worth more than the extra strictness on
six, so: `BY DEFAULT` everywhere, and the loader runs `setval` afterwards.
Nothing in the application inserts an explicit id except the job registry.

### Triggers raise `integrity_constraint_violation`

The five refusals in `0030` and `0033` are the mechanism behind settled
decision 4 — nothing becomes evidence without a person. Under SQLite,
`RAISE(ABORT, …)` surfaces in Python as `sqlite3.IntegrityError`, and the
promotion and census test suites assert exactly that.

plpgsql's bare `RAISE EXCEPTION` surfaces as `psycopg.errors.RaiseException`,
which descends from `DatabaseError` and **not** from `IntegrityError`. A test
asserting an integrity error would fail, and — worse — a call site catching
`IntegrityError` to turn a refusal into a message for the operator would stop
catching it and let a traceback out instead.

So every one of these raises with
`USING ERRCODE = 'integrity_constraint_violation'`, which psycopg maps to
`IntegrityError`. That is also the honest classification: the trigger is
enforcing an integrity constraint that cannot be written as a `CHECK` because
it spans two tables.

The message text is identical to the SQLite one, character for character. It
is what an operator sees, and it names the file to go and read.

### Ordering

SQLite sorts `NULL` first ascending and last descending. PostgreSQL does the
opposite. Any view here that orders by a nullable column says `NULLS FIRST`
or `NULLS LAST` explicitly, so that neither engine's default is load-bearing.

### Collation

The database is expected to be created with a bytewise collation so that
`ORDER BY name` matches SQLite's `BINARY` ordering:

```sql
CREATE DATABASE sectortrace
    LOCALE_PROVIDER = builtin
    BUILTIN_LOCALE = 'C.UTF-8'
    TEMPLATE = template0;
```

The `builtin` provider (PostgreSQL 17+) is preferred over `LC_COLLATE='C'`
because it is version-stable: a glibc or ICU upgrade on the server can change
collation ordering underneath an existing index, and a project whose whole
purpose is a figure that reproduces in a year should not have its sort order
depend on the host's libc.

## Moving the data across

The schema is what this directory builds. The rows come over separately, with
`pipeline/pgload.py` and `pipeline/pgverify.py`:

```bash
./start.sh migrate-data --dry-run
./start.sh migrate-data
./start.sh verify-migration
```

Four things about that are decisions rather than mechanics, and each is
argued in the module docstrings:

**The load order is parents-first, and it includes edges no foreign key
expresses.** Three triggers ask whether an `evidence_promotions` row exists
and two ask about `census_verifications`, and neither dependency is a column
reference — the first identifies its target by an `<authority>|<url>` string,
the second matches on four columns including a whole line of PDF text. Loading
those two tables first means `COPY` fires every trigger and every one of them
answers yes, so the guarantee behind settled decision 4 is never suspended for
the one operation that writes every evidence row this project has.

**Nothing is cast.** SQLite's type affinity is a suggestion: an INTEGER column
will hold `'n/a'`. The loader refuses such a row, naming it, rather than
deciding what it meant. Same for a NUL byte in text, which PostgreSQL cannot
store and which is not this pipeline's to strip out of archived prose.

**Ids are copied verbatim** — which is why the identity columns are
`GENERATED BY DEFAULT`, above — and every sequence is then moved past them.
Left behind, the next review decision anybody makes fails on a duplicate key,
days later, with nothing connecting it to the migration.

**`schema_migrations` is not copied.** It records which files were applied to
*this* database. The two ledgers legitimately differ, and the SQLite warehouse
can be a file behind the tree while the PostgreSQL one is current.

Verification is separate from the loader on purpose — a copy checked by the
thing that wrote it agrees with itself. It compares row counts, per-column
`NULL` counts, minima and maxima, then every value of every row in
primary-key order, which is also the check that would notice this database
having been created without the collation above.
