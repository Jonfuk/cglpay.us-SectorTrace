Parse failures

Not decidable. A parse failure is a bug report about a parser in this pipeline, not a judgement call — an empty cell with a logged reason is the correct output.

Deciding records a judgement. It does not promote anything into a canonical table.

Keys: j/k move · a approve · r reject · u reset to pending · x select · o open primary source · / search · Ctrl+K jump anywhere

Alias resolution — resolve unmatched names to a canonical authority / provider

Every resolution is a named, append-only decision. A fuzzy match is never applied automatically; a correction is a new decision that supersedes the old one.

A run here is the run pipeline run would do: same dependency waves, same rate limits, same writes. It fetches from live public sources. One at a time — the warehouse has a single write slot.

      Every file is written with a companion .provenance.json.
      Bundle zips whatever is in this directory now — with a
      manifest naming every file, its SHA-256 and the companion that belongs to
      it — so "the evidence" is one download rather than eighteen. It reads the
      directory, not the warehouse: if these files are stale the bundle is
      stale by exactly the same amount.
      Pushing Sheets tabs to Google stays on the command line: it writes to a
      shared document and needs credentials and someone watching.

Read-only SQL

      

        Runs on a connection opened mode=ro with
        query_only, so nothing typed here can modify the
        warehouse. One statement at a time; results are capped at 500 rows and
        queries are stopped after 20 seconds.
        This reads restricted_ tables like any other
        — the confirmation in the browser tab guards against opening one by
        accident, not against asking for it.
